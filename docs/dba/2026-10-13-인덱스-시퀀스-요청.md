# DBA 요청: 목록 조회 인덱스와 감사 로그 시퀀스 (2026-10-13)

애플리케이션만으로는 줄일 수 없는 DB 비용이다. 모두 **운영 DB 에서 DBA 가 판단·적용**한다.
`docker/init/*.sql` 은 운영 스키마를 따라야 하므로 여기 적은 것을 미리 넣지 않았다.

## 1. 고객사별 목록 인덱스

관리 화면의 목록은 모두 `COMPANY_IDX = :고객사` 를 걸고, 행이 많은 로그 목록은 기본 정렬이 `IDX DESC` 다
(2026-10-13 변경, 시각 정렬은 머리글로 고를 때만). 지금은 `COMPANY_IDX` 인덱스가 없어 PK 를 거꾸로 읽으며
행마다 고객사를 거른다. 고객사 행이 드문 날일수록 많이 읽는다.

| 테이블 | 기본 목록용 | 기간 검색·시각 정렬용 |
|---|---|---|
| CCFA_AUDIT_LOG | `(COMPANY_IDX, IDX)` | `(COMPANY_IDX, CREATEDTIME)` |
| SIGN | `(COMPANY_IDX, IDX)` | `(COMPANY_IDX, CREATETIME)` |
| CHALLENGE | `(COMPANY_IDX, IDX)` | `(COMPANY_IDX, CREATETIME)` |
| TRANSACTIONHASH | `(COMPANY_IDX, IDX)` | `(COMPANY_IDX, CREATETIME)` |
| TRANSACTION_CONFIRMATION | `(COMPANY_IDX, IDX)` | `(COMPANY_IDX, CREATEDTIME)` |
| FIDO_LOGS_yyyymmdd (날짜별) | `(COMPANY_IDX, IDX)` | — (FIDO 로그는 IDX 정렬 고정) |

- `IDX` 는 오름차순 인덱스로 충분하다. Oracle 이 거꾸로 읽는다(INDEX RANGE SCAN DESCENDING + STOPKEY).
- 둘 중 하나만 고른다면 **기본 목록용** `(COMPANY_IDX, IDX)` 이 효과가 크다. 화면을 열 때 매번 타는 쿼리다.
- FIDO_LOGS 는 FIDO 서버가 날짜마다 테이블을 만든다. 인덱스도 테이블 생성 스크립트(FIDO 서버 쪽)에 넣어야 한다.
- INSERT 가 많은 테이블이다. 인덱스 하나당 INSERT 비용이 늘어나는 것을 FIDO 서버 처리량과 함께 본다.

기타 후보(행 수를 확인한 뒤 판단):

- `USERINFO (COMPANY_IDX, USERID, SERVICENAME)`
- `FIDO_STATISTICS (COMPANY_IDX, GROUPBY, CREATEDTIME)`

```sql
-- 예시. 이름·테이블스페이스는 운영 규칙을 따른다.
CREATE INDEX IX_CCFA_AUDIT_LOG_CO_IDX      ON CCFA_AUDIT_LOG (COMPANY_IDX, IDX) ONLINE;
CREATE INDEX IX_SIGN_CO_IDX                ON SIGN (COMPANY_IDX, IDX) ONLINE;
CREATE INDEX IX_CHALLENGE_CO_IDX           ON CHALLENGE (COMPANY_IDX, IDX) ONLINE;
CREATE INDEX IX_TRANSACTIONHASH_CO_IDX     ON TRANSACTIONHASH (COMPANY_IDX, IDX) ONLINE;
CREATE INDEX IX_TRANSACTION_CONF_CO_IDX    ON TRANSACTION_CONFIRMATION (COMPANY_IDX, IDX) ONLINE;
```

## 2. 감사 로그 시퀀스

관리 화면은 상세 화면을 열 때마다 CCFA_AUDIT_LOG 에 한 행을 넣고, 행마다 `SEQ.NEXTVAL` 을 따로 왕복한다
(엔티티 `allocationSize = 1`). 다른 테이블의 INSERT 는 드물어 대상이 아니다.

두 단계 중 하나를 고른다.

**(a) 앱 변경 없음 — 시퀀스 캐시만 켠다.** 지금 `NOCACHE` 라면 NEXTVAL 마다 딕셔너리를 갱신한다.

```sql
ALTER SEQUENCE CCFA_AUDIT_LOG_SEQ CACHE 100;
```

**(b) 왕복까지 줄인다 — INCREMENT BY 와 allocationSize 를 함께 올린다.**
반드시 이 순서로, 같은 배포 창에서 한다. 순서가 어긋나면 IDX 중복(PK 위반)으로 감사 기록이 실패한다.

1. 앱 중지
2. DBA: `ALTER SEQUENCE CCFA_AUDIT_LOG_SEQ INCREMENT BY 50;`
3. 앱: `CcfaAuditLog` 의 `@SequenceGenerator(... allocationSize = 50)` 로 바꾼 버전 배포
4. 앱 기동 후 감사 로그 몇 건이 정상 저장되는지 확인

- 다른 시스템이 같은 시퀀스로 CCFA_AUDIT_LOG 에 넣어도 충돌하지 않는다(Hibernate pooled 방식은 받은 값 아래 50개를 쓴다).
  IDX 에 큰 간격이 생기는 것은 정상이다.
- 시퀀스 이름은 아직 임시(`<TABLE>_SEQ`)다. 실제 이름은 README "시퀀스 이름 교체" 의 쿼리로 확인한다.
