# KBFIDO 스키마 테이블 존치 검토

- 작성일: 2026-09-18
- 대상: KBFIDO 스키마 39개 테이블
- 근거: `docs/erd/kbfido-columns.txt` (ERD 추출본), 로컬 검증 DB 구조
- **상태: 검토 요청. 이 문서는 결정이 아니라 확인이 필요한 목록이다.**

## 왜 이 문서가 필요한가

FIDO Admin 은 스키마를 바꾸지 않는다는 전제로 만들었다(설계서 1.1). 그래서 39개
테이블을 모두 엔티티로 매핑했고, 그중 9개는 **화면 없이 엔티티만** 존재한다.

엔티티만 있다는 것은 "쓰지 않지만 스키마에 있어서 매핑했다"는 뜻이다. 그런 테이블이
정말 필요한지는 스키마를 아는 사람이 판단해야 한다. 아래는 그 판단에 필요한 근거를
모은 것이다.

**중요**: 행 수는 로컬 검증 DB(시드 데이터) 기준이므로 존치 판단의 근거가 되지
않는다. 아래 판단은 전부 **구조와 이름**에 근거한다. 운영 DB 실측이 필요한 항목은
그렇게 표시했다.

## A. 우선 확인 — 보안 관점에서 시급하다

### A-1. `BAK_FIDO_LOGS_BAK` — 복호화된 로그 사본

| 항목 | 내용 |
|---|---|
| 컬럼 | 7 (원본 `FIDO_LOGS` 6 + `DEC_JSONDATA`) |
| 화면 | 없음 |
| ERD 주석 | "로그 백업본 (복호화 컬럼 포함)" |

`FIDO_LOGS.JSONDATA` 는 FIDO 처리 로그다. 여기에는 인증 요청과 응답이 담기며
크리덴셜 식별자, 서명값, 거래 내용이 들어갈 수 있다. 이 백업본에는 원본에 없는
**`DEC_JSONDATA`(복호화 데이터)** 컬럼이 하나 더 있다.

**확인할 것**
1. 원본 `JSONDATA` 는 암호화 저장인가? 그렇다면 `DEC_JSONDATA` 는 같은 내용을
   평문으로 들고 있는 것이다.
2. 이 테이블에 접근 가능한 계정은 누구인가? 원본보다 약한 통제를 받고 있지 않은가?
3. 왜 만들어졌는가? 일회성 장애 분석이었다면 이미 목적을 다했을 가능성이 높다.

**권고**: 평문 사본이 맞다면 존치 여부를 가장 먼저 결정해야 한다. 필요 없다면
삭제, 필요하다면 접근 통제와 보존 기간을 명시해야 한다. FIDO 인증 데이터는
개인정보와 결합될 수 있어 일반 로그와 다르게 다뤄야 한다.

### A-2. `BAK_FIDO_LOGS_TEST` — 운영 스키마에 있는 테스트 테이블

| 항목 | 내용 |
|---|---|
| 컬럼 | 6 (`FIDO_LOGS` 와 동일) |
| 화면 | 없음 |
| 인덱스명 | `FIDO_LOGS_PK_TEST` |

이름과 인덱스명이 모두 테스트 용도를 가리킨다. 운영 스키마에 테스트 테이블이
남아 있는 것 자체가 정리 대상이다. 구조가 로그 원본과 같으므로 실제 로그가
들어 있을 수 있다.

**확인할 것**: 운영 DB 에 데이터가 있는가?

```sql
SELECT COUNT(*) FROM BAK_FIDO_LOGS_TEST;
SELECT MIN(CREATEDTIME), MAX(CREATEDTIME) FROM BAK_FIDO_LOGS_TEST;
```

비어 있으면 삭제, 데이터가 있으면 왜 쌓이고 있는지부터 확인해야 한다.

### A-3. `AWS_INFO` — 마켓플레이스 토큰

| 항목 | 내용 |
|---|---|
| 컬럼 | 10 |
| 화면 | 없음 (설계서에서 의도적으로 제외) |
| 민감 컬럼 | `AMZ_TOKEN` (ERD 에 "민감정보" 표시) |

AWS 마켓플레이스 연동 정보다. **이 제품이 AWS 마켓플레이스로 판매되고 있는가**가
핵심 질문이다. 아니라면 토큰을 담는 테이블이 이유 없이 남아 있는 것이다.

`EXPIRATIONDATE` 가 `VARCHAR2(100)` 이라 만료 여부를 DB 에서 판단하기 어렵다는
점도 함께 봐야 한다.

**확인할 것**: 연동이 현재 운영 중인가? 아니라면 토큰을 폐기하고 테이블을 정리한다.

## B. 아카이브 설계 — 방식 자체를 재검토할 것

### B-1. `FIDO_LOGS_20210101`, `FIDO_LOGS_20210102`

| 항목 | 내용 |
|---|---|
| 컬럼 | 각 6 (원본과 동일) |
| 화면 | 없음 |
| ERD 주석 | "일자별 로그 아카이브. **실제로는 파티셔닝 전환을 검토할 것**" |

ERD 작성자가 이미 문제를 지적해 두었다. 날짜별로 테이블을 만드는 방식은 두 가지
문제가 있다.

1. **이름이 2021년에 멈춰 있다.** 이 방식이 계속 쓰였다면 지금쯤 수백 개의
   테이블이 있어야 한다. 두 개뿐이라는 것은 중단되었다는 뜻이다. 그렇다면 2021년
   이틀치 로그만 남은 셈이다.
2. **조회가 불가능하다.** 기간 검색을 하려면 테이블 이름을 동적으로 만들어야 한다.
   FIDO Admin 의 로그 화면이 이 테이블들을 다루지 못하는 이유다.

**확인할 것**
- 2021년 이후 아카이브는 어디에 있는가? 다른 방식으로 옮겼는가?
- 이 두 테이블의 데이터는 아직 보존 의무가 있는가?

**권고**: 보존이 필요하면 Oracle 파티셔닝으로 옮기고, 아니면 삭제한다. 지금 상태는
둘 다 아니다.

### B-2. `FIDO_STATISTICS_BAK`

| 항목 | 내용 |
|---|---|
| 컬럼 | 12 (원본 `FIDO_STATISTICS` 와 **완전히 동일**) |
| 화면 | 없음 |

컬럼 구성이 원본과 한 글자도 다르지 않다. 스키마 변경 작업 전에 뜬 임시 사본으로
보인다. 통계는 원본 로그에서 다시 집계할 수 있으므로 백업의 가치가 낮다.

**확인할 것**: 언제 만들어졌는가? 원본과 데이터가 같은가?

```sql
SELECT COUNT(*) FROM FIDO_STATISTICS;
SELECT COUNT(*) FROM FIDO_STATISTICS_BAK;
```

## C. 미사용 의심 — 기능이 살아 있는지 확인할 것

### C-1. `CCFA_STATISTICS` + `CCFA_STATISTICS_FILTER` + `CCFA_STATISTICS_ORDER`

| 테이블 | 컬럼 | 역할 |
|---|---|---|
| `CCFA_STATISTICS` | 16 | 어드민 통계 위젯 정의 |
| `CCFA_STATISTICS_FILTER` | 5 | 위젯의 필터 조건 |
| `CCFA_STATISTICS_ORDER` | 3 | 위젯의 정렬 정의 |

세 테이블이 한 덩어리다. 사용자가 대시보드 위젯을 직접 정의하는 기능을 위한
구조로 보인다. `OWNER_IDX`, `OPEN_TYPE('close')`, `GROUP1_IDX`/`GROUP2_IDX` 같은
컬럼이 그 해석을 뒷받침한다.

**새 FIDO Admin 의 대시보드는 이 테이블들을 쓰지 않는다.** `FIDO_STATISTICS` 를
직접 집계한다. 즉 구 어드민의 기능이고, 새 어드민으로 대체되었다.

**확인할 것**
- 구 어드민을 계속 운영하는가? 병행 기간이 끝나면 이 세 테이블도 함께 정리 대상이다.
- 사용자가 만든 위젯 정의가 실제로 들어 있는가? 있다면 마이그레이션 대상인지 판단이 필요하다.

### C-2. `CCFA_MAILING` — 발송 주체가 불분명하다

| 항목 | 내용 |
|---|---|
| 컬럼 | 10 |
| 화면 | 있음 (조회 전용) |

메일과 SMS 발송 큐다. FIDO Admin 은 이 테이블을 **읽기만 한다**. 실제 발송은 다른
시스템이 한다는 전제로 만들었다.

**확인할 것**: 그 발송 주체가 지금도 동작하는가? 아무도 읽어 가지 않는다면 큐에
쌓이기만 하고 메일은 나가지 않는다. 가입 승인 알림을 넣을지 판단할 때도 이 답이
필요하다.

```sql
SELECT STATUS, COUNT(*) FROM CCFA_MAILING GROUP BY STATUS;
SELECT MAX(SENDTIME) FROM CCFA_MAILING;
```

마지막 발송 시각이 오래되었다면 발송 주체가 멈춘 것이다.

### C-3. `CCFA_MENU`, `CCFA_FIELDS` — 코드와 데이터가 이중으로 메뉴를 정의한다

| 테이블 | 컬럼 | 비고 |
|---|---|---|
| `CCFA_MENU` | 13 | 어드민 메뉴 트리 |
| `CCFA_FIELDS` | 9 | 화면 필드 메타 정의 |

FIDO Admin 의 메뉴는 **코드에 고정되어 있다**(`MenuRegistry`). `CCFA_MENU` 는
화면에서 편집할 수 있지만 그 값이 실제 사이드바에 반영되지 않는다. 데이터로만
다루는 셈이다.

`CCFA_FIELDS` 도 마찬가지로 화면 필드를 데이터로 정의하려던 구조인데, 새 어드민은
Thymeleaf 템플릿에 직접 쓴다.

**이것은 결함이 아니라 의도된 설계다**(설계서 3.3). 다만 운영자가 메뉴 정의 화면에서
값을 바꾸고 "왜 화면이 안 바뀌지?" 하고 혼란을 겪을 수 있다.

**확인할 것**: 구 어드민이 이 테이블들을 읽는가? 그렇다면 두 어드민이 서로 다른
메뉴 정의를 쓰는 상태다. 아니라면 이 화면들은 편집 기능을 없애고 조회 전용으로
바꾸거나, 화면 자체를 빼는 편이 혼란이 적다.

## D. 확인만 하고 넘어갈 것 — 현재 구조가 타당하다

| 테이블 | 판단 |
|---|---|
| `FIDO_LOGS`, `CCFA_AUDIT_LOG`, `CCFA_EXCEPTIONS` | append-only 로그. 보존 기간 정책만 확인 |
| `USERINFO`, `CHALLENGE`, `SIGN`, `TRANSACTIONHASH`, `TRANSACTION_CONFIRMATION` | FIDO 프로토콜 핵심. 필수 |
| `CRITERIA`, `CCFA_CRITERIA` | UAF 인증기기 정책. 둘의 역할 분담만 확인 |
| `FIDO2_*` 3종 | FIDO2/WebAuthn 필수 |
| `CCFA_COMPANY`, `CCFA_MANAGER`, `CCFA_MANAGER_PW_POLICY` | 테넌트와 계정. 필수 |
| `APPID`, `APPSERVER`, `CCFA_FDS_POLICY`, `CCFA_LICENSE` | 고객사 운영 데이터. 필수 |
| `CCFA_SYSTEM_PROP`, `CCFA_SYSTEM_INFO`, `CCFA_ERROR_TABLE`, `CCFA_FIDOCLIENT` | 시스템 설정. 필수 |
| `CCFA_OPTION`, `CCFA_OPTIONS` | 코드 사전. 필수 |
| `FIDO_STATISTICS` | 대시보드 집계원. 필수 |

### D-1. 보존 기간은 별도로 확인해야 한다

로그 계열 테이블에 **보존 기간 정책이 보이지 않는다**. `FIDO_LOGS` 는 append-only 로
계속 쌓이고, 오래된 행을 지우는 장치가 스키마에도 코드에도 없다.

전자금융거래 관련 기록은 법정 보존 기간이 있고, 반대로 개인정보는 목적 달성 후
파기해야 한다. 두 요구가 충돌하므로 테이블별로 기간을 정해야 한다.

**확인할 것**: 각 로그 테이블의 보존 기간과 파기 절차가 문서화되어 있는가?

## 확인용 질의 모음

운영 DB 에서 실행해 위 판단의 근거를 채울 수 있다. **읽기 전용이다.**

```sql
-- 1) 의심 테이블의 실제 규모와 최신 데이터 시점
SELECT 'BAK_FIDO_LOGS_BAK'   AS 테이블, COUNT(*) AS 행수, MAX(CREATEDTIME) AS 최신 FROM BAK_FIDO_LOGS_BAK
UNION ALL SELECT 'BAK_FIDO_LOGS_TEST',  COUNT(*), MAX(CREATEDTIME) FROM BAK_FIDO_LOGS_TEST
UNION ALL SELECT 'FIDO_LOGS_20210101',  COUNT(*), MAX(CREATEDTIME) FROM FIDO_LOGS_20210101
UNION ALL SELECT 'FIDO_LOGS_20210102',  COUNT(*), MAX(CREATEDTIME) FROM FIDO_LOGS_20210102
UNION ALL SELECT 'AWS_INFO',            COUNT(*), MAX(CREATEDTIME) FROM AWS_INFO;

-- 2) 통계 백업본이 원본과 같은가
SELECT COUNT(*) AS 원본 FROM FIDO_STATISTICS;
SELECT COUNT(*) AS 백업 FROM FIDO_STATISTICS_BAK;

-- 3) 구 어드민 위젯 정의가 쓰이고 있는가
SELECT COUNT(*) FROM CCFA_STATISTICS;
SELECT COUNT(*) FROM CCFA_STATISTICS_FILTER;
SELECT COUNT(*) FROM CCFA_STATISTICS_ORDER;

-- 4) 메일 발송 주체가 살아 있는가 (SENDTIME 은 VARCHAR2 다)
SELECT STATUS, COUNT(*) FROM CCFA_MAILING GROUP BY STATUS;
SELECT MAX(SENDTIME) FROM CCFA_MAILING;

-- 5) 로그 증가 속도 — 보존 정책 판단용
SELECT TRUNC(CREATEDTIME) AS 일자, COUNT(*) AS 건수
FROM FIDO_LOGS
WHERE CREATEDTIME >= SYSDATE - 30
GROUP BY TRUNC(CREATEDTIME)
ORDER BY 1 DESC;

-- 6) 테이블별 실제 사용 용량
SELECT segment_name, ROUND(bytes/1024/1024, 1) AS MB
FROM user_segments
WHERE segment_type = 'TABLE'
ORDER BY bytes DESC;
```

## 요약

| 구분 | 테이블 | 왜 확인해야 하는가 |
|---|---|---|
| **보안 우선** | `BAK_FIDO_LOGS_BAK` | 복호화 컬럼(`DEC_JSONDATA`)을 가진 로그 사본 |
| | `BAK_FIDO_LOGS_TEST` | 운영 스키마의 테스트 테이블 |
| | `AWS_INFO` | 쓰지 않는 연동의 토큰이 남아 있을 수 있다 |
| **설계 재검토** | `FIDO_LOGS_20210101/02` | 2021년에 멈춘 날짜별 아카이브. 파티셔닝 검토 |
| | `FIDO_STATISTICS_BAK` | 원본과 동일한 임시 사본 |
| **미사용 의심** | `CCFA_STATISTICS` 3종 | 구 어드민 위젯 정의. 새 대시보드는 쓰지 않는다 |
| | `CCFA_MAILING` | 발송 주체가 살아 있는지 불명 |
| | `CCFA_MENU`, `CCFA_FIELDS` | 코드가 메뉴를 정의해 데이터가 반영되지 않는다 |
| **정책 확인** | 로그 계열 전체 | 보존 기간 정책이 보이지 않는다 |

**총 39개 중 11개가 확인 대상이다.** 나머지 28개는 FIDO 프로토콜·테넌트·시스템
설정의 핵심이라 존치가 명확하다.

어떤 테이블도 이 문서만으로 삭제해서는 안 된다. 위 질의로 실제 상태를 확인하고,
각 테이블을 읽는 다른 시스템이 없는지 확인한 뒤 결정해야 한다.
