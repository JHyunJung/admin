# 운영자 가입 신청·승인 설계

**작성일:** 2026-09-17
**대상:** FIDO Admin (Spring Boot 3.5 / Thymeleaf / JPA, Oracle 스키마 동결)
**관련 설계서:** `docs/superpowers/specs/2026-09-16-fido-admin-design.md`

## 1. 목적

지금은 슈퍼 관리자가 운영자를 직접 등록해야만 계정이 생긴다. 사용자가 스스로
가입을 신청하고, 슈퍼 관리자가 승인해야 쓸 수 있는 흐름을 추가한다.

## 2. 고정 제약

| 제약 | 내용 |
|---|---|
| 스키마 | Oracle 스키마 동결. 테이블·컬럼을 추가하지 않는다 (`ddl-auto: none`) |
| 저장 위치 | 신청 정보는 `CCFA_MANAGER` 에 저장한다. 새 테이블을 만들지 않는다 |
| 권한 모델 | `COMPANY_IDX` 가 곧 권한이다. 0 은 슈퍼 관리자를 뜻한다 |
| 화면 | Thymeleaf. 기존 화면 규약(목록·상세·폼, 확인 모달)을 따른다 |

## 3. 상태 모델

신청의 생애주기를 `CCFA_MANAGER.STATUS` 로 나타낸다. 값은 기존 코드가 쓰는
한글 표기를 따른다(`ManagerUserDetailsService.STATUS_ACTIVE = "활성"`).

| 상태 | 의미 | 로그인 | COMPANY_IDX |
|---|---|---|---|
| `승인대기` | 신청 직후 | 불가 | `-1` (미배정) |
| `활성` | 승인 완료 | 가능 | 승인자가 지정한 실제 고객사 |
| `거절` | 반려됨 | 불가 | `-1` 유지 |

### 3.1 로그인 차단은 기존 코드가 담당한다

`ManagerUserDetailsService` 는 이미 `STATUS` 가 `"활성"` 인지로 `enabled` 를
결정한다. 따라서 `승인대기`·`거절` 계정은 **추가 코드 없이** 로그인이 막힌다.
이 동작에 의존하므로, 해당 검사를 바꾸면 안 된다.

### 3.2 미배정 표식은 `-1`

실제 고객사 `IDX` 는 0 이상이므로 `-1` 은 어떤 고객사와도 겹치지 않는다.

`null` 을 쓰지 않는 이유: `CCFA_MANAGER.COMPANY_IDX` 는 NOT NULL 이고,
`null` 은 아래 3.3 의 기존 결함과 맞물려 권한 상승으로 이어진다. 명시적인
음수 표식이 안전하다.

### 3.3 (선행 수정) 기존 결함: `COMPANY_IDX` 가 `null` 이면 슈퍼 관리자가 된다

설계 검토 중 발견한 **기존 코드의 결함**이다. 가입 기능과 별개로 이미 존재한다.

`ManagerUserDetails` 생성자는 `companyIdx == null` 을 권한 상승 위험으로 보고
예외를 던지도록 되어 있다. 그러나 유일한 호출자인 `ManagerUserDetailsService`
가 생성자에 넘기기 전에 `null` 을 `0` 으로 바꾼다.

```java
// ManagerUserDetailsService — null 을 0 으로 치환한다
long companyIdx = m.getCompanyIdx() == null ? 0L : m.getCompanyIdx();
```

`0` 은 `isSuper()` 가 참이 되는 값이므로, `COMPANY_IDX` 가 비어 있는 계정은
막히기는커녕 **슈퍼 관리자로 로그인한다**. 생성자의 방어는 도달하지 않는다.

지금은 관리자만 계정을 만들 수 있어 노출이 제한적이지만, 가입 기능이 생기면
외부 입력이 계정 행을 만들게 되므로 먼저 고친다.

**수정**: `ManagerUserDetailsService` 가 `null` 을 치환하지 않고 그대로 넘겨
생성자의 방어가 동작하게 한다. 그 결과 `COMPANY_IDX` 가 비어 있는 계정은
로그인이 거부된다(권한 상승 대신 차단).

**테스트**: `COMPANY_IDX` 가 `null` 인 계정으로 로그인하면 슈퍼 관리자가 되지
않고 거부되는지 확인한다. 이 테스트는 수정 전에 실패해야 한다.

## 4. 권한 상승 차단 (이 기능의 핵심 위험)

가입 경로로 슈퍼 관리자(`COMPANY_IDX = 0`)가 만들어지는 것이 유일한 심각한
위험이다. 세 겹으로 막는다. 각 방어는 개별 테스트로 검증한다.

1. **신청 시 강제** — 신청 처리는 폼 입력과 무관하게 `STATUS = "승인대기"`,
   `COMPANY_IDX = -1` 로 덮어쓴다. 폼에 소속·상태 입력란 자체를 두지 않으며,
   파라미터로 넘어와도 무시한다.
2. **승인 시 0 거부** — 승인 처리는 지정된 `companyIdx` 가 `0` 이면 거부한다.
   슈퍼 관리자 승격은 이 경로로 불가능하다. 승인 화면의 고객사 선택 목록에서도
   전역(IDX 0) 고객사를 제외한다.
3. **승인 대상 제한** — 승인·거절은 대상이 `승인대기` 일 때만 동작한다.
   이미 `활성` 인 계정의 소속을 이 경로로 바꿀 수 없다.

## 5. 동시성

승인·거절·신청 저장은 경합 구간을 잠금으로 막는다. 기존 운영자 기능이 쓰는
방식을 그대로 따른다.

- **신청 저장**: `LOCK TABLE CCFA_MANAGER IN EXCLUSIVE MODE` 후 `USER_ID` 중복
  재확인 → 저장. (운영자 등록과 동일)
- **승인·거절**: 대상 행을 `PESSIMISTIC_WRITE` 로 잠그고 `STATUS` 를 다시 읽어
  `승인대기` 인지 확인한 뒤 변경한다. 두 관리자가 동시에 처리해도 한 번만
  적용된다. (운영자 잠금 해제와 동일)

## 6. 화면

### 6.1 가입 신청 `/signup` (인증 불필요)

`SecurityConfig` 의 `permitAll` 에 `/signup` 을 추가하고, 로그인 화면에 링크를 단다.

| 항목 | 검증 |
|---|---|
| 아이디 | 필수, 최대 64자, 중복 불가 |
| 비밀번호 | 필수, 8–64자, 영문·숫자·특수문자 모두 포함 |
| 비밀번호 확인 | 비밀번호와 일치 |
| 이름 | 필수, 최대 50자 |
| 이메일 | 필수, 이메일 형식, 최대 256자 |
| 전화 | 선택, 최대 20자 |
| 신청 사유 | 선택, 최대 2048자 → `ETC` 에 저장 |

**소속 고객사 선택란은 없다.** 배정은 승인자의 몫이며, 로그인 전 화면에 고객사
목록을 노출하지 않기 위해서다.

비밀번호 규칙은 운영자 등록 화면(`ManagerController`)의 검증과 동일한 규칙을
공유한다. 새로 만들지 않고 공통 검증으로 뽑아 함께 쓴다.

신청 성공 시 로그인 화면으로 이동하고 "가입 신청이 접수되었습니다. 관리자
승인 후 로그인할 수 있습니다." 를 띄운다.

**아이디가 중복이면 폼 검증 오류로 그 자리에서 알린다**("이미 사용 중인
아이디입니다."). 저장 직전 경합으로 중복이 난 경우에도 500 이 아니라 같은 폼
오류로 돌려준다.

> **받아들인 위험: 계정 열거(account enumeration).**
> 중복을 알려준다는 것은, 공격자가 아이디를 하나씩 넣어보며 그 계정이 있는지
> 확인할 수 있다는 뜻이다(예: `kbadmin` 계정 존재 확인 가능). 그럼에도 이렇게
> 정한 이유는 이 도구가 사내망 전용이고 운영자 계정이 한 자릿수라 실제 노출이
> 작은 반면, 왜 신청이 안 됐는지 모르는 사용자의 비용은 계속 발생하기
> 때문이다. 외부에 노출되는 환경으로 바뀌면 이 판단을 다시 해야 한다.
>
> 초안에는 "중복 여부를 노출하지 않는다" 와 "중복일 때는 폼 검증 오류로
> 알린다" 가 함께 적혀 있었으나 둘은 동시에 성립할 수 없다. 위와 같이
> 정리한다.

### 6.2 가입 승인 `/signups` (SUPER 전용)

`SecurityConfig` 에서 `/signups/**` 를 `hasRole("SUPER")` 로 막고, 사이드바
"운영자" 그룹에 메뉴를 넣는다(아이콘 `bi-person-check`).

- **목록**: `STATUS = "승인대기"` 인 행. 아이디·이름·이메일·전화·신청일시·신청 사유.
  건수가 많지 않으므로 기본 정렬은 신청일시 오름차순(오래된 신청 우선).
- **승인**: 고객사를 선택하고 승인. 선택 목록에서 전역(IDX 0)은 제외한다.
  결과: `STATUS = "활성"`, `COMPANY_IDX = 선택값`, `UPDATEDTIME` 갱신.
- **거절**: 사유를 입력하고 거절. 결과: `STATUS = "거절"`, 사유를 `ETC` 에
  기존 신청 사유와 함께 남긴다(`거절 사유: ...` 를 덧붙인다).

거절된 신청의 삭제는 **기존 운영자 관리 화면의 삭제 기능**을 쓴다. 별도 삭제
기능을 만들지 않는다.

## 7. 범위 밖

- **신청 결과 알림(메일·SMS)**: `CCFA_MAILING` 이 있으나 실제 발송 주체는 이
  관리 도구가 아니라 별도 시스템이다. 승인되면 로그인으로 확인 가능하므로
  이번 범위에서 제외한다.
- **신청 횟수 제한(rate limit)**: 사내망 전용이므로 실질 위험이 낮다고 보고
  넣지 않는다. 외부 노출 환경으로 바뀌면 재검토한다.
- **가입 시 소속 자동 추론(이메일 도메인)**: 고객사별 도메인을 담을 컬럼이
  스키마에 없다.

## 8. 테스트

**선행 수정 (3.3)**
- `COMPANY_IDX` 가 `null` 인 계정으로 로그인하면 슈퍼 관리자가 되지 않고
  거부되는가 (수정 전에는 실패해야 하는 테스트)

**권한 상승 차단 (4장 각 항목마다 1건 이상)**
- 신청 파라미터에 `companyIdx=0`, `status=활성` 을 실어도 저장 결과가
  `COMPANY_IDX = -1`, `STATUS = 승인대기` 인가
- 승인 시 `companyIdx = 0` 이면 거부되는가
- 이미 `활성` 인 계정에 승인이 적용되지 않는가

**인증 흐름**
- `승인대기` 계정으로 로그인하면 실패하는가
- 승인 후 같은 계정으로 로그인하면 성공하고, 소속이 지정한 고객사인가
- `거절` 계정으로 로그인하면 실패하는가

**입력 검증**
- 아이디 중복 시 신청이 거부되는가
- 비밀번호가 정책(8–64자, 영문·숫자·특수문자)에 어긋나면 거부되는가
- 비밀번호 확인이 다르면 거부되는가

**접근 제어**
- 인증 없이 `/signup` 이 열리는가
- 일반 고객사 계정이 `/signups` 에 접근하면 403 인가
- 고객사 계정 사이드바에 가입 승인 메뉴가 보이지 않는가

**동시성 (통합 테스트)**
- 같은 아이디로 동시에 신청하면 하나만 저장되는가
- 같은 신청을 동시에 승인하면 한 번만 적용되는가
