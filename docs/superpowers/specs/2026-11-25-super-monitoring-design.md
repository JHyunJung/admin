# SUPER 관제 화면 설계 (2026-11-25)

## 의도

크로스서트 내부 운영자(SUPER)가 화면 하나를 열어 **어느 고객사에 지금 문제가 있는지**를 바로 알 수 있게 한다.
지금은 SUPER 도 고객사를 하나 골라야 대시보드가 열리고, 그 대시보드는 고른 고객사 하나의 일자별 합계만 보여 준다.
고객사가 여럿이면 하나씩 골라 들어가 봐야 이상을 알 수 있다.

우선순위(사용자 결정):

1. 장애·이상을 빨리 잡는다.
2. 영업·정산용 지표는 그다음이다. 이번 범위에서는 순위표의 숫자가 나중에 그 용도로 이어질 수 있게만 둔다.

## 목표

- 전 고객사를 한 화면에서 본다(고객사 선택 없이 열린다).
- 당일 원본 데이터로 "트래픽이 끊긴 곳", "예외가 튀는 곳"을 보여 준다.
- 통계(어제까지)로 고객사별 인증량·성공률·증감을 보여 주고, 성공률이 떨어진 곳을 표시한다.
- 통계 배치가 멈췄으면 화면 맨 위에서 알린다.

## 하지 않는 것

- 당일 실패율. 통계 배치가 24시간 늦게 쌓이므로(`FidoStatisticsJob.DELAY_HOURS = 24`) 실패율은 어제까지만 본다. 사용자가 받아들였다.
- 메일·문자 알림, 자동 새로고침. 사람이 화면을 열어서 본다.
- 내보내기(CSV 등), 기간 선택. 영업·정산 단계에서 다룬다.
- 통계 배치 변경, 새 테이블·인덱스. DBA 과제와 엮지 않는다.
- 기존 대시보드(`/`)와 `StatisticsQueryService` 변경.
- ~~순위표 행에서 그 고객사를 선택해 기존 화면으로 넘어가는 링크. 다음 단계로 미룬다.~~ 2026-11-25 후속으로 넣었다: 두 표의 고객사 이름을 누르면 그 고객사를 골라(`POST /select-tenant`) 고객사 대시보드로 간다.

## 실패로 보는 것 (동작해도 안 되는 경우)

- COMPANY 운영자가 다른 고객사의 숫자를 볼 수 있다.
- 화면을 열 때마다 당일 로그 테이블을 통째로 읽어 FIDO 서버의 적재에 부담을 준다.
- 데이터가 없거나 읽지 못한 것을 "정상(0건)"으로 보여 준다. 모르는 것은 모른다고 표시한다.
- 주말·새벽처럼 원래 조용한 시간에 경고가 떠서 아무도 경고를 믿지 않게 된다.

## 제약 (코드에서 확인한 것)

- `FIDO_LOGS_yyyyMMdd` 는 FIDO 서버가 날짜마다 만드는 테이블이다. 인덱스는 PK(`IDX`)뿐이고 `CREATEDTIME`·`COMPANY_IDX` 인덱스가 없다. 시간 범위로 걸러도 전체를 읽는다. 로그가 없는 날은 테이블 자체가 없다(`FidoLogTable.exists`).
- 테이블 이름은 `FidoLogTable.nameFor(LocalDate)` 로만 만든다(SQL 에 이어 붙는 유일한 값, 신뢰 경계).
- `JSONDATA` 는 CLOB 이다. 이번 화면은 이 컬럼을 읽지 않는다(건수만 센다).
- `FIDO_STATISTICS.GROUPBY` 는 `yyyy/MM/dd/HH` 문자열이다. 날짜 기준은 GROUPBY 이고 `CREATEDTIME`(적재 시각)이 아니다. 옛 값(`day` 등)은 형식으로 걸러야 한다(`StatisticsQueryService` 주석 참고).
- `CCFA_EXCEPTIONS.CREATEDTIME` 은 `VARCHAR2(64)` 이다. 더미 데이터는 `yyyy-MM-dd HH:mm:ss` 형식이다. **운영 값의 형식은 확인하지 못했다.** 인덱스는 PK 뿐이다.
- `TenantContext.companyIdx()` 는 SUPER 가 고객사를 고르지 않았으면 예외를 던진다. 이 화면은 그 메서드를 쓰지 않는다.
- 접근 제어는 두 겹이다: `SecurityConfig.SUPER_PATHS` 의 URL 매처와 서비스 계층 검사. `ArchitectureRulesTest` 가 `MenuRegistry.superOnly` 와 `SUPER_PATHS` 를 교차 검증한다.
- `JdbcTemplate` 은 Hibernate `jdbc.time_zone` 을 쓰지 않는다. 시각 비교는 `HourlyAggregator` 와 같은 방식(`Timestamp.valueOf`, Asia/Seoul 벽시계)으로 한다.
- 통계의 고객사 범위는 `COMPANY_IDX IN (SELECT IDX FROM CCFA_COMPANY)` 이다(`HourlyAggregator`). 이 화면도 `CCFA_COMPANY` 에 있는 고객사만 다룬다.

## 검토한 방식

| | 방식 | 감지 시점 | 부담 |
|---|---|---|---|
| A | 기존 통계(`FIDO_STATISTICS`)만 쓴다 | 하루 뒤 | 가장 작다 |
| B | 최근 구간은 당일 원본 테이블에서 직접 센다 | 수 분 | 화면을 열 때 당일 테이블을 읽는다 |
| C | 통계 배치의 24시간 지연을 줄인다 | 약 1시간 | 한 번 쌓은 시간대를 다시 세지 않으므로 늦게 들어온 로그가 빠져 숫자가 굳는다. 과거 숫자와의 연속성도 건드린다 |

**선택: A + B(건수만).** 사용자가 골랐다.
당일 구간은 원본에서 건수만 세어 끊김과 예외 급증을 잡고, 실패율·증감은 통계로 어제까지 본다.
C 는 로그 적재 방식 확인이 먼저 필요하고 통계의 의미를 바꾸므로 뺐다.
B 에서 JSON 을 풀어 당일 실패율까지 내는 안은 CLOB 전체를 읽어야 해서 뺐고, 사용자가 당일 실패율은 없어도 된다고 했다.

### "지금" 표의 값

당일 테이블 `FIDO_LOGS_<오늘>` 을 한 번 읽어 고객사·시간별 건수와 마지막 로그 시각을 구한다(JSONDATA 를 읽지 않는다).

- **최근 1시간**: 기준 시각에서 60분 전까지의 건수.
- **기준일 같은 시간**: 기준일 테이블의 같은 60분 구간 건수. 기준일은 7일 전이고, 그 테이블이 없으면 전일이다. 둘 다 없으면 "-" 로 표시하고 끊김·감소 판정을 하지 않는다. 원본끼리 비교하는 이유는 단위가 같아서다 — 통계는 Auth·TC·Reg·DeReg 만 세므로 원본 건수와 맞지 않는다.
- **오늘 누계**, **마지막 로그**: 당일 테이블 기준. 당일 테이블이 없으면 모두 0, 마지막 로그 "-".
- **예외(ERROR)**: `CCFA_EXCEPTIONS` 에서 `E_LEVEL = 'ERROR'` 인 건수를 두 값으로 보여 준다 — 최근 1시간과 오늘 누계. `CREATEDTIME` 이 `yyyy-MM-dd HH:mm:ss` 문자열이면 사전순이 시간순이라 문자열 범위로 건다. (위 스케치의 "오늘 예외" 열은 이 두 값으로 바뀐다. 내 결정이다.)
- **공통 줄**: `COMPANY_IDX` 가 0 이거나 NULL 이거나 `CCFA_COMPANY` 에 없는 예외는 버리지 않고 "공통(고객사 없음)" 한 줄로 모아 표 맨 위에 둔다. DB 연결 끊김 같은 시스템 예외가 여기 모이므로 장애 신호로는 가장 중요하다. 이 줄에는 로그 건수 열이 없다. (내 결정이다.)
- 자정 직후 60분 구간이 전날로 넘어가는 경우는 전날 테이블까지 함께 읽는다(기준일도 같다).

### 상태 판정 (기본값은 내 제안, 설정으로 바꿀 수 있다)

| 상태 | 조건 | 기본값 |
|---|---|---|
| 끊김 | 기준일 같은 시간 건수가 `min-baseline` 이상인데 최근 1시간이 0 | `min-baseline` 20 |
| 감소 | 기준일 같은 시간 건수가 `min-baseline` 이상이고 최근 1시간이 그 `drop-ratio` 미만 | `drop-ratio` 0.5 |
| 예외 급증 | 최근 1시간 ERROR 예외가 `exception-threshold` 이상. 오늘 누계로 판정하면 한 번 넘은 뒤 자정까지 켜져 있고, 평소 예외가 많은 고객사는 매일 뜬다 | 10 |
| 정상 | 위에 해당하지 않고 오늘 로그가 있다 | |
| 트래픽 없음(`-`) | 오늘도 기준일 같은 시간도 0 | |

`min-baseline` 을 두는 이유는 원래 조용한 고객사·시간대에 경고가 뜨지 않게 하기 위해서다.
한 고객사가 여러 조건에 걸리면 위 표의 순서에서 앞선 것을 보여 준다.

설정 키는 `fido-admin.monitoring.*` 로 두고 `StatisticsBatchProperties` 와 같은 방식으로 받는다.

### "최근 7일" 표의 값 (화면 제목은 2026-11-25 에 "어제까지 (통계)" 에서 바꿨다 — 기간이 다 찬 마지막 날에서 끝나 보통 그제까지이기 때문이다)

`FIDO_STATISTICS` 를 GROUPBY 범위로 읽어 고객사별로 합친다. 최근 7일의 끝은 **통계가 있는 마지막 날의 전날**(다 찬 마지막 날)이고, 직전 7일은 그 앞 7일이다.
배치가 시간 단위로 24시간 늦게 쌓으므로 마지막 날은 항상 일부만 차 있다. 그날을 넣으면 덜 찬 7일과 꽉 찬 7일을 비교해 증감이 늘 음수로 치우친다. 표 머리에 실제 기간(날짜)을 적는다. (내 결정이다.)

- 인증량 = `AUTH_S + AUTH_F`, 증감 = 직전 7일 대비 %.
- 인증 성공률 = `AUTH_S / (AUTH_S + AUTH_F)`, 변화 = 직전 7일 대비 %p. 분모가 0 이면 "-".
- 등록 성공률 = `REG_S / (REG_S + REG_F)`.
- 순증 등록 = `REG_S - DEREG_S`.
- 인증 성공률이 `success-drop-points`(기본 5.0)%p 이상 떨어졌고 최근 7일 인증량이 `min-auth`(기본 100) 이상이면 하락 표시를 한다.
- 계산 규칙(반올림, 분모 0)은 `StatTotals.authSuccessRate` 와 같게 한다.

### 집계 멈춤 알림

`FIDO_STATISTICS` 의 최신 시간 형식 GROUPBY 가 `지금 - 24시간 - stale-hours`(기본 3시간) 보다 이전이고, **그 사이 구간에 원본 로그가 한 건이라도 있으면** 화면 맨 위에 알린다.
배치는 로그가 없는 시간에는 행을 만들지 않으므로, 원본 로그 유무를 보지 않으면 새벽·주말처럼 전 고객사가 조용한 구간에서 배치가 정상인데도 알림이 켜진다.
원본 유무는 해당 날짜 테이블(대개 전일)의 시간별 건수로 확인한다. 지난 날짜 테이블은 바뀌지 않으므로 기준일 테이블과 같은 방식으로 보관한다. (내 결정이다.)
통계가 한 건도 없으면 "집계된 통계가 없습니다" 로 알린다.

## 구조

- 새 패키지 `monitoring`: 컨트롤러, 조회 서비스, 표 한 줄을 담는 값 객체, 판정 규칙, 설정 프로퍼티.
- 조회는 읽기 전용 SQL(`NamedParameterJdbcTemplate`)이다. 기존 `StatisticsQueryService` 는 건드리지 않는다.
- 고객사 목록은 `CCFA_COMPANY` 에서 가져와 로그가 없는 고객사도 줄이 생기게 한다(끊김을 보려면 필요하다).
- **상태 판정은 SQL·시계와 분리한 순수 함수로 둔다.** 입력(최근 건수, 기준 건수, 예외 건수, 임계값)만으로 결과가 나오게 해 DB 없이 단위 테스트한다.
- **접근 제어**: `SUPER_PATHS` 에 `/monitoring/**` 를 추가하고 `MenuRegistry` 에 `superOnly` 로 등록한다. 서비스도 `tenant.require().isSuper` 가 아니면 거부한다(두 겹 규칙).
- **부하 제한**: 당일 테이블 조회 결과를 메모리에 60초(`cache-seconds`) 보관하고, 그동안은 다시 읽지 않는다. 기준일 테이블은 내용이 바뀌지 않으므로 날짜가 바뀔 때까지 보관한다. 동시에 여러 요청이 와도 조회는 한 번만 돈다. 서버가 여러 대면 서버마다 따로 보관한다(60초마다 서버당 한 번).
- **조회 시간 상한**: 원본 테이블 조회에는 쿼리 타임아웃(`query-timeout-seconds`, 기본 10초)을 건다. 넘으면 실패로 다룬다. (내 결정이다.)
- **읽지 못한 경우**: 당일 테이블·예외 테이블 조회가 실패하면 그 열을 "확인 불가"로 표시하고 나머지는 보여 준다. 0 으로 채우지 않는다.

## 확인이 필요한 것

아래는 코드로 알 수 없고 운영 DB 를 봐야 하는 것이다. 답에 따라 설계가 바뀐다.

**2026-11-25 사용자 결정: 확인을 기다리지 않고 진행한다.** 구현은 다음 가정 위에 선다 — 로그는 실시간으로 적재되고,
당일 테이블은 60초에 한 번 건수만 전체 읽어도 되는 크기이며, 예외 시각은 `yyyy-MM-dd HH:mm:ss`, 레벨 값은 `ERROR` 다.
가정이 틀렸을 때 코드를 고치지 않고 끌 수 있도록 "지금" 표의 로그 열과 예외 열을 각각 설정으로 끌 수 있게 한다
(`fido-admin.monitoring.live-logs-enabled`, `exceptions-enabled`, 기본 켬). 끄면 그 열은 "사용 안 함"으로 표시한다.
운영 배포 전에 아래 쿼리로 가정을 확인한다.

1. **FIDO 서버가 로그를 실시간으로 넣는가.** "지금" 표 전체가 "최근 60분 건수 = 실제 트래픽"이라는 가정에 서 있다. 모아서 늦게 넣는다면 최근 1시간이 늘 기준일보다 적어 끊김·감소가 상시 오탐이 된다. 그 경우 비교 구간을 뒤로 미루거나 이 표를 다시 설계한다.
2. **운영 당일 로그 테이블의 행 수.** 수십만 건이면 60초 보관으로 충분하다. 수천만 건이면 전체 읽기 대신 `IDX` 이후만 읽는 증분 방식이 필요하다(구조가 달라진다).
3. **운영 `CCFA_EXCEPTIONS`**: `CREATEDTIME` 의 실제 형식, 전체 행 수, `E_LEVEL` 의 실제 값. 형식이 `yyyy-MM-dd HH:mm:ss` 가 아니거나 값이 `ERROR` 가 아니면 예외 건수가 항상 0 으로 나온다. 인덱스가 없어 전체를 읽으므로 행 수가 많으면 이 열을 뺀다.

확인용 쿼리(읽기 전용):

```sql
-- 1·2. 당일 테이블: 행 수, 가장 최근 로그 시각(지금과 몇 분 차이인지), 시간별 분포
SELECT COUNT(*), MAX(CREATEDTIME), SYSTIMESTAMP FROM FIDO_LOGS_20261125;
SELECT TO_CHAR(CREATEDTIME,'HH24') H, COUNT(*) FROM FIDO_LOGS_20261125 GROUP BY TO_CHAR(CREATEDTIME,'HH24') ORDER BY 1;
-- 3. 예외 테이블: 행 수, 시각 형식 표본, 레벨 값, 고객사 없는 행
SELECT COUNT(*) FROM CCFA_EXCEPTIONS;
SELECT CREATEDTIME FROM CCFA_EXCEPTIONS WHERE IDX = (SELECT MAX(IDX) FROM CCFA_EXCEPTIONS);
SELECT E_LEVEL, COUNT(*) FROM CCFA_EXCEPTIONS GROUP BY E_LEVEL;
SELECT COUNT(*) FROM CCFA_EXCEPTIONS WHERE COMPANY_IDX IS NULL OR COMPANY_IDX = 0;
```
