
## 2026-09-17 — 폼 길이 검증은 @Size 가 아니라 @ByteSize

KBFIDO 스키마의 VARCHAR2 는 BYTE 의미다(NLS_LENGTH_SEMANTICS=BYTE, AL32UTF8).
한글 1자 = 3바이트이므로 `@Size(max=N)` 는 문자 수를 세어 통과시킨 뒤 저장 시
ORA-12899 를 낸다. 코드베이스는 이미 `common.ByteSize` 로 이 문제를 해결했다
(@ByteSize 96곳 vs @Size 2곳, @Size 는 비밀번호 전용으로 의도된 문자 수 검증).

- 새 폼의 길이 제약은 **항상 @ByteSize** 를 쓴다.
- 컬럼 여유 계산도 바이트로 한다. "2048 컬럼에 1900자 허용" 같은 문자 기준
  계산은 한글에서 5700바이트가 되어 무의미하다.

## 2026-09-17 — "값을 강제한다"와 "받을 통로가 없다"는 다른 성질이다

`SignupService.apply()` 는 상태·소속을 강제 저장한다. 이 성질은 행동 테스트로
검증된다. 그러나 **파라미터로 받을 통로가 없다**는 더 강한 성질은 행동 테스트로
검증되지 않는다.

검토 중 실험으로 확인했다. `Long companyIdx` 파라미터를 추가하고 호출부에서
`-1L` 을 넘기면, 저장 결과를 보는 테스트는 **전부 통과한다**. 값이 올바르기
때문이다. 그런데 그 파라미터는 `0L`(SUPER)을 받을 수 있는 통로다.
이 경우를 잡은 것은 시그니처를 검사하는 리플렉션 테스트뿐이었다.

- 인증 없이 호출되는 경로에서 "이 값을 외부가 정할 수 없다"가 보안 성질이라면,
  값 검사만으로는 부족하다. 통로의 부재를 직접 검사한다.
- 다만 파라미터 **개수**를 세는 것은 약하다. 타입 집합(예: 전부 String)을
  검사해 `Long`·enum·DTO 가 끼어드는 것을 막는 편이 의도에 가깝다.
- 파라미터 객체로 바꾸는 리팩터링을 한다면, 그 객체에 해당 필드가 없다는 것이
  같은 보장을 더 읽기 쉽게 표현한다.

## 2026-09-17 — 진단용 @Disabled 를 커밋에 흘리지 않는다

디버깅 중 테스트 하나에 `@org.junit.jupiter.api.Disabled("진단 중")` 을 붙였다가
그대로 커밋했다. 하필 그 테스트가 "가입 계정이 SUPER 가 되지 않는다"를 확인하는
핵심 보안 테스트였다. 전체 실행은 BUILD SUCCESSFUL 이었고 실패도 0이라
아무 신호가 없었다. Codex 검토가 잡아냈다.

- `grep "@Disabled"` 로 확인했으나 애너테이션을 **정규화된 이름**으로 붙여서
  걸리지 않았다. 패턴이 아니라 **결과**를 본다: 테스트 XML 의 `skipped` 합계가
  0인지 확인한다.
- 커밋 전 점검: `grep -ho 'skipped="[0-9]*"' build/test-results/test/*.xml`
- "통과했다"는 실행된 테스트에 대해서만 참이다. 건너뛴 테스트는 통과가 아니다.

## 2026-09-18 — 기존 테스트가 "고쳐야 할 동작"을 정당화하고 있을 수 있다

테넌트 격리 작업에서 `CrudService.checkTenant()` 의 SUPER 우회를 제거했다.
그런데 그 우회는 **테스트가 정상 동작으로 단언하고 있었다**.

    @Test void superCanGetAnyTenant() {
        login(0L);
        when(repo.findById(9L)).thenReturn(Optional.of(license(9L, 2L)));  // 소유 = 2
        assertThat(service.get(9L).getCompanyIdx()).isEqualTo(2L);         // 열린다고 단언
    }

같은 성질의 테스트가 다른 파일에도 셋 더 있었다(`UserinfoServiceTest.superCanChangeAnyTenantStatus`,
`FdsPolicyServiceTest.superKeepsChosenCompany`, `SystemPropServiceTest` 의 감사 로그 단언).

- 동작을 바꾸는 작업에서 기존 테스트가 빨개지면, **"셋업이 낡았나"와 "이 테스트가 옛 의미를
  정당화하나"를 먼저 구분한다.** 전자는 셋업만 고치고, 후자는 이름과 단언을 다시 쓴다.
- 구분 없이 일괄로 셋업만 맞추면 **초록 스위트 뒤에 회귀가 숨는다.** 이번 건에서는
  25개 실패 중 3개가 후자였고, 이름(`superCanGetAnyTenant`)이 단서였다.
- `superCan...` 처럼 **권한을 긍정하는 이름**은 격리 작업에서 우선 의심 대상이다.

## 2026-09-18 — 계획서의 코드 샘플은 "읽히는가"가 아니라 "컴파일되는가"로 본다

이번 계획에서 두 건이 나왔다.

- `TenantSelectionInterceptor.preHandle` 샘플이 2인자였다(`Object handler` 누락).
  `HandlerInterceptor` 를 구현할 수 없는 코드였고 구현자가 고쳐서 진행했다.
- `MenuRegistry.areaOf` 샘플이 미등록 경로를 전부 TENANT 로 판정했다.
  `withSlash("/")` 가 `"/"` 라서 모든 경로가 루트 항목에 접두사 일치했고,
  `.orElse(SYSTEM)` 이 도달 불가 코드였다. 주석은 "오탐을 막는다"고 적혀 있었다.

둘 다 읽기에는 자연스러웠다. 후자는 기존 테스트가 **등록된 경로의 하위 경로만** 검증해
비껴갔고, 컨트롤러가 직접 탐침을 짜서야 드러났다.

- 계획에 코드를 넣을 때는 시그니처와 경계값(빈 값, 루트, 미등록)을 손으로 한 번 돌려본다.
- **자신 있는 주석 + 결함을 비껴가는 테스트** 조합은 특히 위험하다. 주석을 믿지 말고
  동작을 실행해 확인한다.

## 2026-09-18 — 화면의 "체크박스 + hidden" 은 브라우저가 보내는 순서까지 확인한다

FIDO 서버 설정 화면의 토글 6종이 **켜지지 않았다.** 화면은 정상으로 보이고 저장도
성공(302)했는데, DB 에는 항상 꺼진 값만 들어갔다.

원인은 폼 필드 순서였다. 체크박스는 켜졌을 때만 전송되므로 같은 이름의 hidden 으로
"끔" 값을 함께 보내는데, 컨트롤러의 `@RequestParam Map<String,String>` 은 중복
파라미터에서 **첫 값만** 취한다(`getParameter` 의 동작). hidden 을 앞에 두면 "켬"이
영영 전달되지 않는다. hidden 을 뒤로 옮겨 고쳤다.

- 이 결함은 **키 이름을 실제 운영 값으로 바꾸기 전부터 있었다.** 기존 웹 테스트가
  텍스트·숫자 파라미터만 단언해서 6개월이든 얼마든 그대로 통과했을 코드다.
- 렌더 결과만 보면 두 input 이 모두 있으니 정상으로 보인다. **중복 이름 파라미터는
  "존재하는가"가 아니라 "어느 것이 바인딩되는가"를 확인해야 한다.**
- 확인 방법: 단정하지 말고 `MockHttpServletRequest` 에 같은 이름을 두 번 넣어
  `getParameter` 가 무엇을 돌려주는지 직접 찍어 본다(임시 프로브 후 삭제).
- 회귀 테스트는 순서를 못 박는 형태로 남긴다 —
  `토글은_체크박스가_hidden_보다_앞에_온다` 는 렌더된 HTML 에서 두 input 의
  인덱스를 비교한다. 순서가 뒤집히면 즉시 깨진다.

교훈: **"저장 성공" 은 "올바른 값이 저장됨" 이 아니다.** 저장 후 DB 를 직접 조회해
값을 눈으로 확인하는 절차가 이 결함을 잡았다. 화면 왕복만 봤다면 기본값과 구분되지
않아 놓쳤을 것이다.

## 2026-09-27 — perl 치환의 `${...}` 는 변수 보간이고, zsh 의 `$VAR` 는 단어 분리를 안 한다

같은 세션에서 셸 도구 습관 두 개가 각각 결함을 만들었다.

1. `perl -pi -e 's|…|th:text="|AAID(정책) #${item.idx}|"|'` — 치환문 안의 `${item.idx}` 를
   perl 이 **변수로 보간**해 빈 값이 됐고, 그 결과가 엉뚱한 줄(`<html lang="ko"`)에 붙어
   템플릿이 깨졌다. 첫 확인에서 "h1 이 안 바뀌었네" 라고만 보고 Edit 로 h1 을 다시 고친 뒤
   넘어갔다. 2번 줄이 망가진 것은 웹 테스트가 `TemplateInputException` 을 내고서야 알았다.
2. `FILES="a b c"; for f in $FILES` — zsh 는 기본으로 `$FILES` 를 분리하지 않아 파일 7개가
   하나의 (없는) 경로로 취급됐다. perl 이 "No such file" 을 냈지만 치환 건수 확인 없이
   테스트를 돌렸고, 같은 8건이 그대로 실패했다.

- Thymeleaf/템플릿 문자열(`${…}`, `#{…}`, `@{…}`)을 perl 치환문에 넣지 않는다. `\$` 로
  이스케이프하거나, **처음부터 Edit 도구를 쓴다.** "매칭 안 됨" 처럼 보여도 실제로는
  다른 곳을 건드렸을 수 있으니, perl 치환 뒤에는 `git diff` 로 **바뀐 줄 전체**를 본다.
- zsh 에서 여러 파일을 돌릴 때는 배열(`FILES=(…)`; `"${FILES[@]}"`)을 쓴다.
- 일괄 치환 뒤에는 반드시 **건수를 센다**(`grep -c`). 0 이면 치환이 안 된 것이고,
  기대치와 다르면 패턴이 빗나간 것이다. 테스트가 같은 이유로 또 실패하면 편집이
  적용됐는지부터 의심한다.
- 필드명으로 비밀값을 판별할 때 규칙이 컬럼명 기준(`_PW`)인지 확인한다. `userPw` 는
  `USERPW` 가 되어 걸리지 않는다 — `AuditChanges.columnName` 이 그래서 있다.

## 2026-09-27 — 생성자 의존성을 더하면 그 클래스를 @Import 하는 슬라이스 테스트를 먼저 찾는다

`ManagerUserDetailsService` 에 `LoginAttemptService` 를 주입했더니, 그 서비스를
`@DataJpaTest` + `@Import` 로 끌어오던 통합 테스트 15건이 컨텍스트 로딩에 실패했다.
단위 테스트는 생성자 호출을 grep 해 고쳤지만 `@Import` 는 놓쳤다 — 컴파일은 통과하고
실행해야 드러난다. 같은 세션 앞부분의 `AuditReadInterceptor` 건(@WebMvcTest 284건)과
같은 유형이다.

- 서비스 생성자에 협력자를 더할 때는 `new X(` 뿐 아니라 `@Import.*X\.class` 도 grep 한다.
- 슬라이스에 새 협력자를 함께 `@Import` 하면 된다. 협력자가 부수 작업(감사 로그 등)이면
  `ObjectProvider` 로 받아 없을 때 건너뛰게 하는 편이 낫고, 핵심 로직(잠금 판정)이면
  실제 빈을 넣어 기존 단언이 의미를 잃지 않게 한다 — mock 으로 넣으면 "항상 안 잠김"이 된다.
- `verify(repo).delete(any())` 는 `JpaSpecificationExecutor.delete(Specification)` 과
  모호하다. `any(Entity.class)` 로 쓴다.
